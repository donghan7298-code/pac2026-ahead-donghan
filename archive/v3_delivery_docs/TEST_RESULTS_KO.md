# 팀 연동 검사와 모델 성능을 읽는 방법

2026-10-09 실제 실행 결과: 동한 98개 통과/0개 생략,
팀 202개 통과/4개 생략, 두 검사 모두 실패 0개다.
팀의 생략 4개는 gymnasium/torch 의존성이 없는 환경에서 실행하지 못한 검사다.
생략은 통과로 세지 않는다.

| 비교 | 동한 검사 | 팀 검사 |
|---|---|---|
| 주요 범위 | 후보 평가·학습 데이터·모델 계약·팀 adapter·측정 결과 계약 | 후보 생성·기하·hard mask·고수준 정책·runtime·로봇 검사 |
| 코드 검사 수 | 98 | 202 |
| 후보 생성/기하/hard mask만의 검사 수 | 다른 구성으로 분산됨 | 30+47+43 = 120 |
| 실행된 검사 통과율 | 100% | 100% |
| 실제 ROS2/MoveIt pick-place | 이번 환경에서 미실행 | 이 pytest 결과로 입증하지 않음 |

통과 개수는 서로 다른 시험의 문제 수와 같다. 많은 개수가 더 높은 모델 점수를 뜻하지 않는다.
또한 한 함수를 여러 박스 크기·회전·하중 조건으로 반복 검사하면 개수가 늘어난다.
모듈을 연결한 검사는 import/type/state_version/EMS 계약을 지키는지 확인하며,
선택한 위치가 DBLF보다 더 효율적인지는 별도 실험으로 확인해야 한다.

예를 들어 max_top_load=0 N인 박스에 상자를 올리는 후보를 **거절하면** 그 코드 검사는 통과다.
그 검사에서 상자를 실제로 적재했다는 의미는 아니다. 98개에는 실제 작은 Bullet 검사 3개도
포함되지만, 이것도 로봇으로 98회 집기·적재를 했다는 의미가 아니다.

내 파트가 개선됐는지는 같은 미학습 박스 순서로 DBLF·동한 heuristic·학습 모델을
비교하여 판단한다. 다음 항목을 함께 본다.

1. 성공한 박스 수와 사용한 팔레트 수
2. 충돌·지지 부족·하중 초과와 물리 검사 결과
3. 실행 가능한 후보 비율, 버퍼/팔레트 교체 필요 여부
4. 계획 시간과 모델 fallback 발생
5. 실제 ROS2 trajectory 성공, payload 상승, release, 측정 상태 commit

현재 실제 Bullet 측정 상태 루프에서 동한 h3/s7은 원본 6개를 두 종류의 팔레트에
완료했다. DBLF는 원본 8개를 완료했다. 동한 8개는 7번째에서 버퍼가 필요해 정지했다.
두 검사 모두 통과했어도 실제 행동 결과는 다를 수 있다는 사례다.

새 데이터는 180개 scenario/14,400개 source box, 26,906개 query,
377,767개 candidate label까지 실제 수집했다. 학습·held-out 비교의 진행 상태는
[v3 검증 기록](../reports/integration_v3_20261009.json)을 확인한다.
더 많은 데이터나 epoch 자체를 성능 개선의 증거로 쓰지 않는다.

회의에서는 이렇게 설명할 수 있다:

> 코드 연동 검사에서는 실행한 항목이 모두 통과했습니다. 검사 개수 차이는 담당 범위와
> 테스트 구성 차이입니다. 적재 성능은 같은 박스로 baseline과 비교하고, 로봇 시연은
> 실제 MoveIt 실행과 측정 상태 갱신을 따로 검증하겠습니다.
